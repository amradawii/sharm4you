# My-Photos: Download All (server-side zip + AJAX loader) + Lightbox Slider

Add a server-side "Download All" zip button to /my-photos with a Google Drive-style AJAX loader (delivery_code passed in POST body, not session-flash; set_time_limit guard; temp file auto-deleted after send) plus a lightbox slider reusing the existing gallery-album pattern with a per-photo download button inside it.

## Summary

Two enhancements to the `/my-photos` tourist delivery page: (1) a "Download All" button that generates a server-side zip of all booking photos and streams it to the user via AJAX (Google Drive-style loader on the button, temp file auto-deleted after send, no cron, no persistence), and (2) a lightbox slider reusing the existing gallery-album lightbox pattern with a per-photo download button inside it.

## Design decision: Download All — server-side zip with AJAX loader (confirmed)

**Approach:** Server-side zip generation with immediate cleanup, triggered via AJAX for a Google Drive-style loader UX.

**Why server-side over client-side (JSZip):**
- **CORS:** JSZip needs `fetch()` to R2 presigned URLs, which requires CORS headers on the R2 bucket. The current `<a download>` works because it's a navigation, not XHR. Server-side zip fetches from R2 server-to-server (fast datacenter connection, no CORS).
- **Mobile memory:** Zipping 30 photos in JS on mobile is risky (iOS Safari tab crashes). PHP with 512M handles it easily.
- **Mobile network:** Server-side = tourist downloads one file. Client-side = tourist fetches 30 files then zips in JS.

**Loader UX (Google Drive pattern):**
1. Click "Download All" → button shows spinner + "Preparing..." immediately
2. AJAX `fetch()` POSTs `booking_number` + `delivery_code` to the server
3. Server generates zip (a few seconds)
4. Response arrives as a blob → JS creates object URL → triggers `<a download>`
5. Button shows "Downloaded!" briefly → returns to normal
6. Object URL revoked to free memory

The `fetch()` goes to our own server (not R2), so no CORS issues. The blob (~30-90MB for 30 photos) sits in memory only briefly before being saved — fine on modern phones.

## Implementation

### 1. Download All — server-side zip with AJAX loader

#### Route (`routes/web.php`)

Add to both the root and `{locale}` groups:

```php
Route::post('/my-photos/download-all', [PhotoDeliveryController::class, 'downloadAll'])
    ->middleware('throttle:3,1')
    ->name('my-photos.download-all');
```

#### Controller (`app/Http/Controllers/PhotoDeliveryController.php`)

**Refactor:** Extract the booking lookup + `hash_equals` validation into a private `resolveBooking(Request $request): ?Booking` method so `show()` and `downloadAll()` share the exact same logic (DRY, no drift).

New `downloadAll(Request $request)` method:
1. Get `booking_number` + `delivery_code` from request input (both sent from the page — same trust level as the presigned URLs already exposed in `<img src>`/`<a href>` on the same page).
2. Call `resolveBooking()` — if invalid, return JSON `{ success: false, message: ... }` with 422 (AJAX-friendly, no redirect).
3. `set_time_limit(120)` — guard against 30 sequential R2 fetches exceeding PHP's default 30s `max_execution_time` if R2 is slow. One-line guard, not a queue/job.
4. Load photos ordered by `sort_order`.
5. Create temp zip: `tempnam(sys_get_temp_dir(), 'sharm4you_')` + rename to `.zip`.
6. Open `ZipArchive`, loop photos: `Storage::disk('r2')->get($r2_key)` → `addFromString($original_name, $content)`. One file at a time (photos ~1-3MB each, 30 max = ~90MB peak, within 512M).
7. Close zip, return `response()->download($zipPath, $booking->booking_number.'-photos.zip')->deleteFileAfterSend(true)`.
8. **try/catch:** On any exception, delete the temp file and rethrow (never leak temp files).

#### View (`resources/views/my-photos.blade.php`)

Add a "Download All" button (Alpine-managed, not a plain form) next to the photo count badge. Both `booking_number` and `delivery_code` are passed as data attributes / Alpine state — same trust level as the presigned URLs already on the page. No session-flash indirection (flash expires after one request and would silently break the button on refresh/navigation, a common mobile failure).

```blade
<button type="button" class="btn-primary gap-2" @click="downloadAll()" :disabled="downloading">
    <template x-if="!downloading">
        <span class="flex items-center gap-2">
            <svg>...download icon...</svg>
            {{ __('site.my_photos.download_all') }}
        </span>
    </template>
    <template x-if="downloading">
        <span class="flex items-center gap-2">
            <svg class="animate-spin">...spinner...</svg>
            <span x-text="downloadLabel"></span>
        </span>
    </template>
</button>
```

Alpine state includes: `bookingNumber` (from `$booking->booking_number`), `deliveryCode` (from `$booking->delivery_code`), `downloadAllUrl` (from route), `csrf` (from meta tag), `downloading: false`, `downloadLabel: ''`.

Alpine method `downloadAll()`:
```js
async downloadAll() {
    this.downloading = true
    this.downloadLabel = preparingLabel  // localized "Preparing..."
    try {
        const res = await fetch(this.downloadAllUrl, {
            method: 'POST',
            headers: {
                'Content-Type': 'application/json',
                'X-CSRF-TOKEN': this.csrf,
                'Accept': 'application/json',
            },
            body: JSON.stringify({
                booking_number: this.bookingNumber,
                delivery_code: this.deliveryCode,
            }),
        })
        if (!res.ok) {
            const data = await res.json().catch(() => ({}))
            window.showToast('error', data.message || 'Download failed.')
            return
        }
        // Server returned the zip file as a blob.
        const blob = await res.blob()
        const url = URL.createObjectURL(blob)
        const a = document.createElement('a')
        a.href = url
        a.download = this.bookingNumber + '-photos.zip'
        document.body.appendChild(a)
        a.click()
        document.body.removeChild(a)
        URL.revokeObjectURL(url)
        this.downloadLabel = doneLabel  // localized "Downloaded!"
        setTimeout(() => { this.downloading = false }, 2000)
    } catch (e) {
        window.showToast('error', 'Network error. Please try again.')
    } finally {
        if (this.downloading) this.downloading = false  // safety net
    }
}
```

## Risks / considerations

- **Memory (server):** 30 photos × ~3MB = ~90MB peak via `addFromString`. With 512M limit this is safe. If photos were ever much larger, switch to `addFile` with per-photo temp files (more complex, not needed now).
- **Memory (browser):** The blob (~30-90MB) sits in JS memory briefly before being saved. Modern phones handle this fine. Object URL is revoked immediately after download to free memory.
- **Execution time:** 30 sequential R2 fetches could exceed PHP's default 30s `max_execution_time`. `set_time_limit(120)` at the top of `downloadAll()` guards against this. Not worth a queue/job at this scale.
- **Temp file cleanup:** `deleteFileAfterSend(true)` handles the happy path. try/catch deletes the temp file on any exception before the response is created, so a failure mid-zip never leaks a file.
- **delivery_code in page source:** The code is in the page alongside presigned download URLs that already grant 24h access with zero auth. Hiding the code while exposing everything it protects would be inconsistent. Both `booking_number` and `delivery_code` are sent in the AJAX POST — same trust level, no session-lifetime footgun.
- **UX change:** Clicking a photo now opens the lightbox instead of downloading directly. Intentional and better UX — per-photo download is still available via the lightbox button.
- **AJAX vs form submit:** Using `fetch()` + blob gives us the loader UX. The trade-off is the blob sits in memory briefly, but this is acceptable for the file sizes involved and gives the Google Drive experience the user wants.

## Explicitly out of scope

Client-side zipping (JSZip — CORS + mobile memory issues), streaming zip libraries (ZipStream-PHP), session-flash for delivery_code (fragile, inconsistent security model), changing the presigned URL TTL, changing the admin upload cap, adding CORS headers to R2, adding `response-content-disposition` headers to R2, per-photo temp files (not needed at current photo sizes), cron-based cleanup (not needed — cleanup is immediate), queue/job-based zip generation (not needed at 30-photo scale).
